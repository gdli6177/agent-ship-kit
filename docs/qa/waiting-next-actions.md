# 等待事项操作验收

日期：2026-11-04。基于 v0.4.2 修复。

## 原因

等待中的目标把“更新下一步”“记录决定”和“记录进展”藏在手动表单中。编辑安排虽然能恢复状态，却不是清晰的动作；`goal.progress` 还可能只写记录而不通知管家。普通等待目标也没有要求立即核查进展或修改提醒的直接入口。

## 操作

- 「有结果了，继续推进」只需填写一句最新结果与下一步。「交给管家继续」保存为进行中，清除等待对象、旧提醒和已过期跟进注意力，保留原负责人现场并要求优先恢复；「我来处理」不派发。
- 「请管家跟进」保持等待对象与提醒，要求管家联系原负责人核查实际结果，不能把催办写成等待已结束，也不代替人联系外部审批者。
- 「稍后提醒我」可选择 1 小时、24 小时或未来的自定义时间；保留等待状态，到时间再进入注意力。
- 等待中的请求决定及管家决定直接在等待操作区展示。旧「更新下一步」表单仍保留给高级修改，不再是推进的必要路径。
- 高级手动操作明确分为「补充进展」「编辑目标」「提交成果」。补充进展不覆盖原定的下一步，编辑目标不提交验收，提交成果必须附真实检查。

## 状态与通知

恢复与跟进使用持久化的 `dispatch` 请求，有 `pending`、`sent`、`failed` 三种可见状态。消息发送前先保存更新，失败保留内容和重试入口；打开工作区会重试尚未完成的请求。每次请求有独立 ID，旧消息回执不能覆盖更新的恢复、跟进或人工接管。重复请求在后台合并，成功送达后不再自动补发同一请求。

管家更新消息明确包含用户补充的结果；跟进消息要求保持等待与提醒。管家是否实际核查和执行由 Agent 行为约束，不能仅以消息送达宣称外部人员已经回复。

## 验证

`packages/core/test/waiting.test.ts` 与 `apps/desktop/test/goal-delivery.test.ts` 覆盖恢复、跟进、稍后提醒、手动接管、离线失败和重试、旧回执、并发新请求、重启读取及结束目标拒绝恢复。

`pnpm test:desktop` 通过真实打包界面完成等待、设置提醒和手动恢复；`pnpm test:onboarding` 通过真实可交互 CLI 验证恢复消息、跟进消息实际进入 stdin，并核对目标状态与提醒保留。自定义 CLI fixture 证明真实消息传输，不冒充真实模型已经理解或完成。

完整桌面试用、首次启动和安装包验收均已通过。类型检查与 49 项单元测试通过；DMG、ZIP 完成 SHA-256、严格签名、下载隔离、安装启动、图标和内置 CLI 写入验证。首轮桌面回归发现到期跟进注意力遮住了恢复后的普通进展入口，已修正等待状态的操作边界并重跑。新增 onboarding 用例在关闭目标后需先回到设置，再执行原有的打开 Herdr 验证。

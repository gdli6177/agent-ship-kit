## 最终通知策略守卫的补充实跑

完整双工人试用后，最终源码又收紧了 captain 通知的策略路径。用最终 `scripts/host-pre-tool.mjs` 启动真实 CLI 子进程，对第二轮临时状态根补做三项探针：

- 把 `.agent-ship/packets/` 下自写文件作为 policy/allowlist：退出 2，拒绝。
- 使用状态根 `.agent-ship/notify.policy.md` 和 `notify.allowlist.json`：守卫退出 0，仍须通过通知策略本身的检查。
- captain 文件工具写受保护 allowlist：退出 2，拒绝。

证据为同目录 `final-hook-probes.json`。这些探针只判断工具准入，没有发送消息。完整自动测试也覆盖通知路径替换、伪装 CLI、预算重置和受保护写入；此处明确区分最后一项守卫补丁与前面的安装归档。

## 3、4、更多需求的容量验证

自动回归创建 **五个**独立 owner/lane、冻结合同和 worktree：A/B/C 运行时 D/E 保留为 frozen；D 的第四个工人因 global_max_parallel 拒绝。取消 A 后 D 可以启动；E 仍拒绝。登记 human 批准上限 4 后 E 才启动，此时四个工人运行。需求数量没有写死为 2；工人容量是跨 lane 共享的准入约束，超额不会自动排队启动。

同时验证重复认领不能把 lane 指针退回第一版方案；同 lane 更新后，旧合同不能再派发新工人；另一 lane 的新需求不影响本 lane。

## 验证边界

真实运行覆盖 macOS launchd 与上述 OMP 路由；Linux cron、其它编排器及各宿主 UI 的自动技能发现仍只有对应自动测试/文档约定，没有逐一实机试用。通用 hook 不自动安装到各宿主；宿主必须转换原生工具事件、绑定已认证 actor、阻断非零结果并保护文件/环境。自填环境变量不是人类认证，同一 OS 用户的任意文件写入不在 CLI 应用守卫的安全边界内。

需求队列与角色卡不会创建运行时、自动 drain 队列或提高并发。Captain 每轮处理队列，适配器负责真实启动/停止实例。没有自动冻结、最终验收、合并或部署。
